# kx-opc-web

> 新部署说明：OPC 数据改为写入 `kayex_data`，默认保留 365 天；手工初始化不包含程序自动创建的表，也不包含 OPC 晶棒/炉次台账。界面保持不变，相关晶棒功能暂可能无数据。部署与配置以根目录 `DEPLOYMENT.md` 为准。


OPC 服务可视化网站：查看炉台实时数据、实时 / 历史曲线、历史数据导出、通讯预警与告警记录、按晶棒导出、上位机记录，并合并了原 TDengine 取数网站（Flask 版 TD_frontend）的 PLC / CCD 取数和硬件信息（全量数据导出）。要登录，内部账户看全部功能，客户账户只看上位机数据和上位机记录（见下文“账户”）。
OPC 数据来自 TDengine 库 `kayex_data` 里 kx-opc-client 写入的 `opc_data`，不直连炉台；PLC / CCD 数据来自 `kayex_data`。Go 单程序，前端打包后嵌在程序里，端口 **8700**。

## 页面

左侧菜单按数据来源分两组：**OPC 监控**的数据来自 `kayex_data`（kx-opc-client 采集的 `opc_data`），顶部的炉台选择框只在这一组显示，选中的炉台这一组共用；**全量数据导出**的数据来自 `kayex_data`（PLC `dbcenter_data`、CCD `hmi_ccddata`）和 `sop_hardware`，页面里自己选设备，设备清单读 `kayex_data` 的标签，和 OPC 的炉台清单不是一份。

| 菜单 | 说明 |
|---|---|
| OPC 监控 · 曲线显示（实时曲线 / 历史曲线：按时间、按晶棒） | 选中的点位（最多 10 个）**画在同一张图里**，每个点位各用自己的纵轴，图铺满页面下方：可框选放大、双击还原、点图例隐藏曲线；**单击图或点“放大”弹出大图**。**历史**：按时间（最长 2 小时）或按晶棒（可选工步，背后画工步色带）查询、导出 CSV。**实时**：打开就画，先从数据库补最近 10 分钟 ~ 2 小时，再接上每秒推送的数据；离开页面就停止，不在后台记录 |
| OPC 监控 · 数据管理 · 查看数据 | 两个标签。**实时数据**：表格显示当前炉台的全部点位，每秒刷新，变化的值闪一下；可筛选全部 / 关注 / 数值 / 开关量 / 文本，星标的排在最前。**历史数据**：选时间（最长 31 天）和点位（最多 10 个，文本点位也可以）查询，表格按 **默认每页 10 条，可选 10 / 20 / 50 / 100 条或自定义 1–1000 条**查询，可首页、上一页、下一页、尾页或输入页码跳转；已选点位标签可拖动排序（也支持 Alt + 左右方向键），顺序保存在本机，表格和 CSV 沿用此顺序 |

| OPC 监控 · 通讯预警 | **当前状态**：全部炉台的心跳和工控机时钟，每 5 秒刷新，异常的排在最前；超过一半炉台同时心跳停止时提示先查采集程序。**告警记录**：按时间（最长 31 天）、炉台、类型查询每次告警的开始、恢复和持续时长，可导出 CSV，可点“看曲线”跳到曲线。侧栏的红色数字是当前有告警的炉台数 |

| OPC 监控 · 配置信息 | **点位信息**：每个点位（`opc_data` 的列名，就是 OPC 的 tag）对应的中文名和 DB 点位，全站显示和导出表头都用它；页面只读，**下载 CSV 改好后上传**，或直接在数据库里 INSERT，见下文“点位信息”。**客户可见点位**：勾选客户账户“上位机数据”里能看的点位 |

| 上位机 · 上位机数据（只有客户账户） | 就是“查看数据”页（实时数据 + 历史数据），只有客户可见的点位 |

导出的 CSV 带 UTF-8 BOM，Excel 直接打开不乱码，表头为“中文名 [点位]”，边查边写，不占内存。

## 账户

账户写在 `config.yaml` 的 `accounts` 里（改完重启生效），登录页 `/#/login`，登录 `session_ttl`（默认 12 小时）后要重新登录。`accounts` 为空则不需要登录，所有人按内部账户。

| 角色 | 能看什么 |
|---|---|
| `admin` 内部账户 | 全部功能，含上位机记录、配置信息里的客户可见点位 |
| `customer` 客户 | 只有**上位机数据**（管理员勾选的点位：实时数据、历史数据、导出）和**上位机记录**，全部炉台。后端按账户限制：别的接口返回 403，点位列表、点位信息、实时推送、历史查询都只有客户可见的点位 |

登录后发一个签名的 Cookie（用户名 + 过期时间 + HMAC），服务端不存会话，重启程序不用重新登录；签名密钥由全部账户的用户名、密码、角色算出，改了密码或删了账户，之前的登录自动失效。

## 点位信息

存在 `kayex_data.opc_point_info`，没有配置的点位直接显示列名。两种修改方式，效果一样：

1. **上传 CSV**：“点位信息”页点“下载 CSV”得到全部点位，在 Excel 里填好后上传。表头 `点位,中文名,DB点位`，列的顺序不限，可以只有其中两列（没有的列不改）；UTF-8 和 Excel 默认的 GBK 编码都认。只修改文件里出现的点位，没有变化的不写库。只有内部账户能上传。
2. **直接写数据库**：插一行即可，每个点位以最新一行为准，网站每分钟重新读一次：

```sql
INSERT INTO kayex_data.opc_point_info (ts, point, name, db_point) VALUES (NOW, 'MELT_TEMP_PV', '熔体温度', '33.124-0');
```

## 数据表

网站和采集客户端共用库 `kayex_data`。网站自己的两张表是**普通表**，主键为 (ts, 第二列) 复合主键，启动时自动创建（已存在则跳过），**每一列都用 zstd 高压缩**，建表 SQL 见 `sql/web_tables.sql`：

| 表 | 用途 | 列（加粗为复合主键） |
|---|---|---|
| `opc_point_info` | 点位信息：每次修改追加一行，每个点位的最新一行为当前值；`customer` 为客户可见（早期建的表启动时自动补这一列） | **`ts`、`point`**、`name`、`db_point`、`customer` |
| `web_alarm` | 告警事件：只在状态变化时写，触发、恢复各一行（几百台炉台一天通常只有几行到几十行） | **`ts`、`device_ip`**、`device_id`、`alarm_type`、`active`、`seconds` |

- 旧版本的 `web_config`（显示字段、模板）已不再使用，表里没有数据，确认后可以 `DROP TABLE kayex_data.web_config`。
- 同一台炉台同一时刻的两条告警（心跳停止和时间不一致）主键相同，程序会把第二条错开 1 毫秒写入。

## 告警怎么判定

每 5 秒检查一轮（`monitor.interval`），状态变化时才写 `web_alarm`，触发、恢复各一行：

| 类型 | 触发 | 恢复 | `seconds` |
|---|---|---|---|
| `heartbeat_stop` 心跳停止（红色） | `HEART_UTC_TIME` 超过 60 秒没变化（`monitor.heartbeat_timeout`） | 心跳重新变化 | 触发时：已停多少秒；恢复时：一共停了多少秒 |
| `time_skew` 时间不一致（黄色） | 与基准时间相差超过 30 分钟（`monitor.clock_skew_limit`），**连续 3 轮**（`alarm.skew_confirm`） | 连续 3 轮不超限 | 当时的时间差（工控机快为正） |

- 心跳停止期间不判断时间差（这时算不出来），已有的时间不一致告警保持不变。
- 告警的 `ts` 用 TD 服务器时钟，与采集数据一致，可以直接对照历史曲线。
- 程序重启后先从 `web_alarm` 读回每台炉台每种告警的最后一行，接着判定，不会重复触发；读不到之前不判定。
- 写 TD 失败时事件留在内存（最多 2 万条），下一轮重试；主键是 (ts, device_ip)，重试写到同一行，不会重复。
- **同一时间只能运行一个 kx-opc-web 实例**写告警，否则同一次告警会被记两遍。
- 列名特意避开了 TDengine 关键字（如 `value`），手写 SQL 不用加反引号。
- 库的 KEEP 是 365 天，配置行会由程序定期重写，避免长期没改的配置过期。

## 晶棒数据导出

数据来自 kx-inner-processor：它给 `opc_data` 每行补了 `inner_crystal_no`（晶编号）、`inner_furnace_no`（炉次号）、`is_first`（首棒），并维护晶棒台账 `inner_crystal_info`。列名、台账表名、工步名称在 `config.yaml` 的 `crystal` 段。

- **晶棒列表以主表为准**：按晶编号汇总行数，再补上台账信息。台账只记“看得到开头”的晶棒，inner-processor 上线时正在拉的那一根不在台账里，同样能导出。
- **时长都按上位机心跳算**（`monitor.heartbeat_column`，默认 `HEART_UTC_TIME`）：心跳是上位机按自己的时钟每秒写的，不受采集端服务器时钟被改写的影响。晶棒时长 = 心跳从第一行到最后一行的跨度。
- **工步时长是每次停留的总和**：工步常常来回跳（实测 BB001 一根晶 23.0 料筒提出 ↔ 24.1 二次加料交替 8 次），所以不能用“第一次进入到最后一次离开”的跨度。程序按时间顺序逐行扫工步号和心跳，相邻两行的心跳差算给前一行的工步；差值超过 `crystal.gap_limit`（默认 1 分钟，采集中断）的记为断数，不计入任何工步。所有工步时长之和 + 断数 = 晶棒时长。页面同时显示每个工步**进入了几次**，并画出工步时间线（每一段是一次连续停留，宽度按时长）。
- **工步**按工步号（一位小数）分别统计和筛选：21.0 渣盖提出、21.1 粘渣准备、21.2 放断提出是不同的工步。名称和主 / 子工步在 `crystal.step_names` 里配置。工步号是 FLOAT，按 ×10 取整比较（`ROUND(STATE * 10)`）。
- **导出**按 1 小时一段查询、边查边写，不占内存；中途失败时文件最后一行写“导出中断，数据不完整”。

PLC / CCD 取数也可以**按晶棒导出**：用 kayex_data 自己的晶棒台账 `kayex_data.inner_crystal_info`（编号与 OPC 台账不是同一套，`extract.crystal_ledger` 配置），查询区间就是这根晶在台账里的起止 ts，其余（点位、CCD 关联、分段、各种导出）和按时间取数完全一样。晶棒时长按台账的采集时间（capture_time，PLC 时钟）算。

## 与原取数网站的对照

PLC / CCD 取数和硬件信息是原取数网站（Flask，:8600）的 Go 重写，**导出文件与原网站逐字节一致**，可以直接替换原网站，下游处理脚本不用改。

**怎么验证的**

1. 开发时把原网站的函数（关联、分段、炉次晶棒状态机、写 CSV）原样复制出来，用 pandas 处理 5 组构造的数据（含 .5 秒取整、CCD 同一秒多行、空值、整数值的浮点、停炉 / 冷启动 / 结束段 / 手动工步），与 Go 版逐字节对照（对照测试已按要求从仓库删除）。
2. 2026-10-29 连真实库，新旧两个网站同一条件（10.65.104.57，2026-10-27 07:00 起 24 小时，94194 行）：按秒对齐、最近时刻、只取 PLC 三种模式下，查询返回的行数、列、分段、前 1000 行都相同，**全量 CSV、分炉次 / 晶棒 CSV、全部分段 zip 里的文件都逐字节相同**；硬件信息的查询和导出也逐字节相同。

**有意的不同**

| | 原网站 | 新网站 |
|---|---|---|
| 数据库连接 | 页面上填，密码会出现在网页里 | 在 `config.yaml` 里配置，页面上没有 |
| 设备 IP | 直接拼进 SQL | 转义后再拼，不能注入 |
| 查询结果 | 最近 30 次的全部数据都放在内存里 | 写成临时文件（`cache/`，1 小时后删除），同时最多 2 个查询，内存峰值可控 |
| 最近时刻关联，CCD 同一采集时间有多行 | 取哪一行取决于 numpy 不稳定排序的实现，没有确定答案 | 固定取按时间顺序最近的那一行 |
| 分炉次 / 晶棒导出，工步点位没起名“工步” | 找不到工步列，原样导出不划分 | 用点位 33.0-0 对应的列划分 |
| 导出文件名 | `filename=` | `filename*=UTF-8''`（中文文件名不乱码），名字相同 |

## 时间怎么算

服务器时钟不可信（晶品 171 慢约 4 分钟，而且被虚拟化平台每分钟改写），所以：

- **基准时间**：程序每 5 分钟向 NTP（`ntp.aliyun.com` 等）取一次标准时间，NTP 不通改用 HTTPS 响应头的 Date；之后用单调时钟推算，**不修改系统时钟**，也不受系统时钟被改写的影响。都不通时页面显示“基准时间未校准”。
- **TD 时钟**：每 5 秒用 `SELECT NOW()` 测一次 TD 服务器比基准时间快 / 慢多少，页面右上角显示。数据的 `ts` 是 TD 服务器时钟打的，换算成基准时间后再和心跳比较。
- **时间差** = `HEART_UTC_TIME` −（这一行到达采集端的基准时间）；心跳值只精确到秒。心跳停止的炉台不判断时间差。
- 页面和曲线上显示的时间仍是 `ts` 原值（TD 服务器时钟），与历史查询一致。

## 实时数据怎么取

- 浏览器通过 WebSocket（`/ws`）订阅当前炉台；后端每秒用**一条 SQL** 取所有被订阅炉台的最新一行（`LAST_ROW`，走 TD 缓存），同一台炉台不论多少人在看只查一次，没人看就不查。
- `ts` 没变不推送；变了只推送变化的点位（通常 80 多个点位里每秒变 20 个左右），新订阅者先收到一份全量。
- 浏览器太慢、发送队列满了就断开，前端自动重连，不会拖慢其他人。

| `GET /api/crystals/steps?table=&crystal=&from=&to=` | 一根晶各工步的时长（按心跳、来回跳累加）、进入次数、行数，以及工步时间线 |
| `GET /api/export?table=&from=&to=[&cols=A,B]` | OPC 全量导出 CSV（不限晶棒，最长 31 天） |
| `GET /api/crystals/export?table=&crystal=&from=&to=[&steps=13,14][&cols=A,B]` | 整棒 / 按工步导出 CSV（cols 为空导出全部点位） |
| `GET /api/points` | 点位信息（点位 -> 中文名、DB 点位、是否客户可见） |
| `POST /api/points/customer` | 设置客户可见的点位：`{"points":[...]}`，没列出的都取消 |
| `GET /api/points/export` | 下载全部点位的 CSV |
| `POST /api/points/import` | 上传 CSV（请求体为文件内容，UTF-8 或 GBK） |

## 构建与部署

开发机上（Windows 用 Git Bash，需要 Go 和 Node）：

```bash
./scripts/build.sh 1.0.0
```

把 `dist/kx_opc_web-1.0.0-linux-amd64.tar.gz` 拷到服务器上解压并安装：

```bash
tar xzf kx_opc_web-1.0.0-linux-amd64.tar.gz && cd kx_opc_web-1.0.0-linux-amd64 && sudo ./deploy/install.sh
```

启动后浏览器打开 `http://<服务器IP>:8700`：

```bash
sudo systemctl start kx_opc_web
```

查看日志：

```bash
journalctl -u kx_opc_web -f
```

配置在 `/opt/kx_opc_web/config.yaml`，每项都有注释。**每次安装都用安装包里的 `config.yaml` 覆盖**，原来的配置备份为 `config.yaml.bak.时间`，所以要改配置请改仓库里的 `configs/config.yaml` 再打包。服务限制内存 512MB（`MemoryLimit`），实际运行约几十 MB。

## 本机开发

先启动后端，再启动前端开发服务器，浏览器打开 `http://localhost:5173`，接口自动代理到 8700。

**本机后端和 171 上的正式实例连的是同一个库，告警只能有一个实例写**：本机用的配置要把 `alarm.record` 改成 `false`（照常判定和显示，只是不写 `web_alarm`），否则告警会记两遍。只改前端时也可以不起本机后端，让开发服务器直接代理到 171：`KX_BACKEND=10.65.104.171:8700 npm run dev`。

```bash
go run ./cmd/kx-opc-web -config <alarm.record 为 false 的配置>
```

```bash
cd web && npm install && npm run dev
```

## 目录结构

```

  config/             config.yaml 加载与校验
  auth/               账户登录、签名 Cookie
  td/                 TDengine 查询封装：结果扫描、点位列表缓存、值的 JSON 规整；网站自建表（tables.go）
  clock/              基准时间：NTP / HTTPS Date 校准，单调时钟推算
  monitor/            炉台目录与心跳、时间差检查
  points/             点位信息（opc_point_info 表）、CSV 导入导出
  history/            历史查询（曲线按列、表格分页）与 CSV 导出
  hmi/                上位机记录（kayex_data 的操作记录、报警记录）查询与导出
  alarm/              告警判定（tracker.go）、写入 web_alarm、告警记录
  crystal/            晶棒列表、工步统计、整棒 / 按工步导出
  extract/            原取数网站：取数、PLC / CCD 关联、工步分段、炉次晶棒划分、与 pandas 一致的 CSV
  realtime/           WebSocket 实时推送
  web/                HTTP 路由，内嵌前端（dist/ 为打包结果）
web/                  前端源码（Vue 3 + uPlot）
deploy/ scripts/ sql/ 部署脚本、构建脚本、网站自建表的 SQL
```

## 同一网段的 A/B 分区

areas 改用 from/to/area 范围规则；默认 A 区 172.30.3.61–65（5 台），B 区 172.30.3.71–130（60 台），不再使用 prefix。
实时监控由后端按范围标记分区，PLC/CCD 的设备选择使用相同的数值 IP 匹配，硬件查询的数据来源不变。
旧版配置需替换为新的范围格式，其他页面布局和功能保持原样。
